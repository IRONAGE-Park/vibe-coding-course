# 강의 중 라이브 업데이트 소재

4장(업데이트 배포)은 강의 도중 이 사이트를 실제로 고쳐 배포하면서 진행합니다.
그때 쓸 만한 소재를 골라 정리했습니다. 하나만 고르면 됩니다.

---

## 고르는 기준

라이브 데모는 잘 되는 것보다 **안 망가지는 것**이 중요합니다. 다음을 모두 만족하는 것만 고릅니다.

| 기준 | 왜 |
|------|-----|
| 참가자 화면에서 **눈에 바로 보인다** | 배포가 반영된 걸 다 같이 확인해야 합니다 |
| **한 파일** 안에서 끝난다 | 여러 파일을 건드리면 되돌리기가 번거롭습니다 |
| 실패해도 **읽는 데 지장이 없다** | 참가자들이 그 사이트로 실습 중입니다 |
| 5분 안에 끝난다 | 2.5시간 실습 시간을 잡아먹으면 안 됩니다 |
| 설명할 **교훈이 있다** | 그냥 색만 바꾸면 배울 게 없습니다 |

---

## 추천 1. 모바일에서 깨진 상단 메뉴 고치기 ★ 가장 추천

**지금 실제로 있는 버그입니다.** 폭 390px 근처(휴대폰)에서 상단 메뉴 글자가 세로로 한 자씩 쪼개집니다. 메뉴 5개와 "막혔을 때" 버튼, 테마 토글이 한 줄에 안 들어가서 생긴 문제입니다.

- **왜 좋은가** — 만들어낸 예제가 아니라 진짜 버그입니다. "AI가 짠 코드에도 이런 게 남는다"는 말을 실물로 보여줄 수 있습니다. 참가자 대부분이 폰으로 확인 가능하니 **각자 자기 화면에서 전후를 볼 수 있습니다.**
- **교훈** — 만들 때 안 보이던 문제가 다른 화면 크기에서 나온다. 그래서 확인이 필요하다.

```
지금 화면은 그대로 두고, 상단 메뉴만 고쳐줘.
폭이 좁은 휴대폰에서 메뉴 글자가 세로로 쪼개져서 읽을 수가 없어.
좁은 화면에서는 가로 스크롤이 되게 하거나 메뉴를 접어서,
글자가 한 줄에 온전히 보이게 해줘.
```

- **확인 방법** — 브라우저 개발자 도구에서 폭을 390px로 줄이거나, 그냥 자기 폰으로 접속
- **되돌리기** — `Nav.tsx` 한 파일만 바뀌므로 Vercel에서 이전 버전으로 되돌리면 끝
- **예상 시간** — 3~5분

## 추천 2. 오늘 강의 안내 배너 붙이기

첫 화면 맨 위에 "점심 13:00~14:00", "5분 뒤 3장 시작" 같은 안내 줄을 하나 넣습니다.

- **왜 좋은가** — 위험이 거의 없고, **그 자리에서 쓸모가 생깁니다.** 배포한 걸 바로 써먹는 경험이 인상에 남습니다.
- **교훈** — 배포는 큰 행사가 아니라 필요할 때 하는 일이다.

```
지금 화면은 그대로 두고, 첫 화면 맨 위에 안내 줄을 하나 추가해줘.
내용은 "○○○" 이고, 눈에 띄되 본문을 가리지 않게.
모바일에서도 글자가 잘리지 않아야 해.
```

- **확인 방법** — 첫 화면 새로고침
- **예상 시간** — 2~3분

## 추천 3. "막혔을 때" 페이지에 방금 나온 진짜 질문 추가하기

오전에 참가자들이 실제로 막혔던 것 하나를 골라 5장 도움말에 항목으로 추가합니다.

- **왜 좋은가** — 강의 중에 쌓인 재료를 그대로 씁니다. 참가자가 "내가 물어본 게 사이트에 올라갔다"고 느낍니다.
- **교훈** — 서비스는 쓰는 사람을 보고 자란다. 업데이트의 이유는 대개 사용자에게서 나온다.

```
지금 화면은 그대로 두고, 막혔을 때 페이지에 항목을 하나 추가해줘.
증상은 "○○○", 원인은 "○○○", 해결은 "○○○".
기존 항목들과 같은 형식으로 맞춰줘.
```

- **확인 방법** — `/help` 페이지에서 새 항목 확인
- **예상 시간** — 3~4분

## 추천 4. 전체 단계를 다 끝낸 사람에게 축하 화면 보여주기

31단계를 모두 완료하면 마지막에 축하 문구가 뜨게 합니다.

- **왜 좋은가** — 오후에 실제로 도달하는 팀이 나오므로 **강의 후반에 효과가 살아납니다.**
- **교훈** — 사용자가 끝까지 갔을 때 무엇을 보여줄지도 설계의 일부다.
- **주의** — 진행 상황 집계 코드를 건드리므로 앞의 셋보다 위험이 큽니다. 시간이 넉넉할 때만.

```
지금 화면은 그대로 두고, 31단계를 모두 완료했을 때만
마지막 단계 아래에 축하 문구를 보여줘.
아직 안 끝난 사람에게는 보이지 않아야 해.
```

- **예상 시간** — 5~7분

## 강의 중 진행 순서

1. **왜 고치는지 한 문장으로** 말하고 시작합니다. ("폰으로 보신 분, 메뉴가 이상하죠?")
2. 요청 문장을 화면에 띄운 채로 Claude에게 보냅니다. 참가자가 **문장을 보게** 하는 것이 핵심입니다.
3. `npm run dev` 화면에서 전후를 비교합니다. 안 바뀌어야 할 곳부터 봅니다.
4. 오류가 나면 숨기지 말고 **그대로 보여주고** 메시지를 복사해 붙여넣습니다. 여기가 제일 좋은 장면입니다.
5. 커밋하고 푸시합니다.
6. Vercel Deployments에서 Building → Ready를 같이 기다립니다. 15~20초입니다.
7. 참가자들에게 **자기 폰에서 새로고침**하게 합니다.

---

## 하지 말 것

- **여러 개를 한 번에 고치지 않기.** 하나가 실패하면 원인을 못 가립니다.
- **진행 상황 집계나 로그인 쪽 건드리지 않기.** 참가자들이 그 기능으로 실습 중입니다.
- **미리 다 만들어두고 재생하지 않기.** 오류가 나는 장면이 오히려 이 장의 핵심입니다.
- **되돌리기를 안 보여주고 넘어가지 않기.** 마지막에 한 번은 이전 버전으로 되돌렸다가 다시 올려 보이면 "실험해도 된다"는 말이 설득력을 얻습니다.

---

## 미리 준비할 것

- Vercel Deployments 탭을 **미리 열어두기** (전환하며 찾으면 흐름이 끊깁니다)
- 요청 문장을 **미리 적어두기** (즉석에서 쓰면 길어집니다)
- 참가자에게 알려줄 **사이트 주소를 화면에 띄워두기**
- 되돌리기 시연을 대비해 **직전 배포가 Ready 상태인지** 확인

## 끝난 뒤

4장 페이지의 다음 자리에 실제 내용을 채워 넣으면 자료가 완성됩니다.

| 위치 | 채울 것 |
|------|---------|
| 1단계 안내 상자 | 실제로 보낸 요청 문장 |
| 2단계 안내 상자 | 작업 전후 화면 캡처 |
| 3단계 | 실제로 만난 오류 메시지 (있었다면) |

캡처는 `public/captures/update/` 에 넣고 `app/update/page.tsx` 에서 참조합니다.
기존 다크 모드 캡처 파일은 지우지 않고 그대로 두었으니, 필요 없으면 나중에 정리하세요.
