## 0. 요약 (먼저 읽을 3줄)

1. 48장 중 **삭제 20장 · 압축 통합 17장 · 유지 11장**으로 판단했고, 신규 2장을 더해 **최종 17장 / 30분** 구성을 제안한다.
2. 원론(컴퓨터의 탄생·코딩의 가치·컴퓨터공학·Waterfall/Agile·LLM 원리)은 **전부 빼는 것이 아니라 "왜 지금 여러분이 할 수 있는가"를 설명하는 1장**과 **용어 정의 1장**으로만 남긴다. 창업팀에게 필요한 최소한은 *동기 부여 1장 + 공통 어휘 1장*이며, 그 이상은 실습 성과에 기여하지 않는다.
3. 남는 시간 전부를 **"좋은 문제 정의"** 로 몰아준다 — 판정 기준(획득/가공) → 라이브 판정 → 세 관문 → **입력·처리·출력·현실의 행동 4칸** → 팀별 문장 리라이트까지 이어지는 하나의 흐름으로 재배치한다.

## 2. 원론 파트 판단 — 무엇을 남기고 무엇을 뺄 것인가

### 2-1. 판단 기준

이 강의의 성공 지표는 "창업팀 10팀이 17:30에 각자 배포 가능한 MVP를 손에 쥐고 나가는가"이다.
따라서 각 슬라이드에 던진 질문은 하나다 — **"이 장이 없으면 팀의 결과물이 나빠지는가?"**

이 기준을 뒷받침하는 근거는 4절의 웹 리서치에 정리했다. 요약하면 (a) 학습의 70%는 실행에서 오고 형식 강의는 10%에 불과하며(70:20:10), (b) 강의식 전달은 10~15분을 넘기면 집중·회상률이 눈에 띄게 떨어지고, (c) 수준 편차가 큰 집단일수록 "설명 → 즉시 적용" 청크가 짧아야 한다. 30분짜리 이론 세션은 **한 덩어리 강의가 아니라 3개 청크(각 8~12분)** 로 설계해야 한다.

### 2-3. 남기는 원론 — 최소한은 무엇인가

원론을 0으로 만들면 두 가지가 깨진다. 그래서 **정확히 2장**만 남긴다.

**① "왜 지금 여러분이 할 수 있는가" 1장 (신규 3장, #6 그래픽 + #8 문구 재활용)**
- 남기는 이유: 수준 편차가 큰 방에서 "나는 못 할 것 같다"는 심리적 진입장벽이 실습 최대의 리스크다. #6의 *기계어 → 어셈블리 → 고급 언어 → 프레임워크 → 자연어* 사다리 그래픽은 "도구는 계속 쉬워져 왔고, 지금 마지막 칸이 자연어"라는 한 장짜리 설득으로 이 리스크를 정면으로 없앤다.
- 빼는 부분: ENIAC 사진, 역사 서술, "코딩은 원래 누구나 할 수 있었다"류의 방어적 문장.

**② 용어 3개 정의 1장 (#23+#24+#25 통합)**
- 남기는 이유: LLM / AI Agent / Vibe coding은 오늘 하루 종일 반복해 쓸 **공통 어휘**다. 정의를 안 맞추면 이후 모든 설명에서 되묻는 비용이 발생한다. 어휘 정렬은 원론이 아니라 **운영 비용 절감**이다.
- 남기는 형태: 각 1줄 정의 + "오늘 우리가 쓰는 것은 Claude Code = 코딩 에이전트" 한 줄. 아이콘 클라우드 3세트는 1세트로 축소.
- 빼는 부분: 모델 이름 나열, "생성형 AI가 더 큰 범위" 같은 분류학, Computer Use 언급.

**③ 남기되 성격을 바꾸는 것 — #11, #12**
- #11(CAN/CANNOT), #12(획득/가공 기준)는 형식상 원론처럼 보이지만 실제로는 **"이 아이디어를 오늘 만들 수 있는가"를 판정하는 체크리스트**다. 팀이 2.5시간짜리 MVP 범위를 스스로 자를 때 쓰는 유일한 도구이므로 원론 축소 대상이 아니라 **강화 대상**이다.

### 2-4. 한 줄 판단

> 원론은 **"동기 1장 + 어휘 1장"** 으로 끝낸다. 나머지 원론 시간은 전부 문제 정의로 옮긴다. 기존 48장 중 원론으로 분류되는 14장이 4장(신규 통합 포함)으로 줄어들며, 여기서 확보되는 약 12~14분이 재구성안의 재원이다.

### 3-3. 구성상 바뀐 점 3가지

1. **"좋은 문제 정의"가 전체의 절반 이상을 차지한다.** 청크 B+C 합계 22분 / 30분 = 73%. 기존 48장에서 문제 정의 관련은 실질 6장(#36,#37,#38,#45,#46 + #21)에 불과했다.
2. **#45(입력·처리·출력·현실의 행동)를 중심 슬라이드로 승격했다.** 기존에는 사례 뒤 뒤편에 묻혀 있었으나, 이 4칸이 팀이 실습 2.5시간 동안 계속 되돌아볼 유일한 틀이다. 3.5분은 전체에서 가장 긴 단일 배정이다.
3. **강의 안에 hands-on을 1회 심었다(신규 14장).** 30분 내내 듣기만 하면 이후 2.5시간의 팀 작업이 백지에서 시작된다. 여기서 문제 문장을 확정해두면 "기본 제작 1h" 구간이 곧바로 굴러간다.

## 4. 근거 자료 (웹 리서치)

### 4-1. 실습 비중 — 70:20:10

- 학습의 약 70%는 실무 경험, 20%는 타인과의 상호작용, 10%만이 형식 교육에서 온다는 모델. 1980년대 Center for Creative Leadership의 Lombardo·Eichinger·McCall이 임원 200명 조사에서 도출했고 30년 이상 검증되어 왔다.
  - [Training Industry — The 70-20-10 Model for Learning and Development](https://trainingindustry.com/wiki/content-development/the-702010-model-for-learning-and-development/) (지속 갱신 위키)
  - [Docebo — 70 20 10 Learning Model: Guide to Experiential Learning](https://www.docebo.com/learning-network/blog/70-20-10/)
  - [Blossom Learning — Understanding the 70 20 10 Model for Effective Adult Learning](https://blossomlearning.co.uk/understanding-the-70-20-10-model-for-effective-adult-learning)
- **본안 적용**: 4시간 30분 중 이론 30분(11%)은 이미 70:20:10에 거의 정확히 맞는 배분이다. 즉 **30분을 늘릴 이유가 없고, 그 30분 안에서 무엇을 버릴지만 결정하면 된다** — 이번 재구성안이 슬라이드를 늘리지 않고 48→17로 줄인 근거.

### 4-2. 강의 청크 길이 — 10~15분

- "10~15분 집중력 한계"는 단일 상수로 입증된 법칙은 아니지만(Wilson & Korn), 강의 시작 10~15분 이후 주의와 회상률이 뚜렷이 떨어진다는 관찰은 반복 보고된다. 원인은 작업기억 용량과 초두·최신 효과(primacy-recency)로 설명된다. 대응책으로 제시되는 것은 **짧은 세션 분할(chunking), 중간 활동·퀴즈 삽입, 개인 학습과 팀 활동의 교차**다.
  - [Bradbury, N. A. — *Attention span during lectures: 8 seconds, 10 minutes, or more?* Advances in Physiology Education (2016)](https://journals.physiology.org/doi/full/10.1152/advan.00109.2016)
  - [Times Higher Education — Chunking lectures: it's a no brainer](https://www.timeshighereducation.com/campus/chunking-lectures-its-no-brainer)
  - [*Chunked Lectures: A new model for conducting online lectures within IT higher education* (arXiv:1909.03041)](https://arxiv.org/pdf/1909.03041)
- **본안 적용**: 30분을 8분 / 10.5분 / 11.5분 3청크로 나누고, 두 번째·세 번째 청크 사이(새 14장)에 팀 작성 활동을 넣은 근거.

### 4-3. 강의 최소화·실습 최대화 워크숍 모델

- 전체 대상 강의(whole-class instruction)를 제한하고 학습자 실습 시간과 개별 피드백에 시간을 몰아주는 것이 "워크숍 모델"의 기본이다.
  - [Education World — Minimize Lecture, Maximize Learning: Workshop Model](https://www.educationworld.com/a_curr/minimize-lecture-workshop-model.shtml)
- 2026년 부트캠프 세션들도 같은 방향이다 — 질문·워크플로 실습·실제 시나리오 작업에 시간을 배정하는 몰입형 구성.
  - [PDI Technologies — New for Connections Live 2026: A Closer Look at the Boot Camp Sessions](https://pditechnologies.com/blog/new-connections-live-2026-boot-camp-sessions/) (2026)
- **본안 적용**: 도구 설명(#31~#34)을 "쓰기 직전"으로 미룬 근거 — 워크숍 모델은 설명을 실습 시점에 붙인다.

### 4-4. 문제 정의(Problem Statement) 워크숍 관행

- 문제 정의 워크숍의 표준 프롬프트는 **누가 영향을 받는가 → 무엇을 하려 하는가 → 무엇이 막고 있는가 → 왜 막히는가 → 그 결과 어떤 영향이 있는가** 다섯 단계이며, 산출물은 "모호한 불만"을 "구체적이고 측정 가능한 과제"로 바꾼 한 문장이다. 통상 90~100분 규모로 진행된다.
  - [Design Sprint Academy — The Problem Statement Workshop](https://www.designsprint.academy/free-templates/the-problem-statement-workshop)
  - [Miro — Customer Problem Statement Examples & Templates](https://miro.com/strategic-planning/customer-problem-statement-examples/)
  - [Institute of Project Management — Problem Statement Template for Project Managers (2026)](https://instituteprojectmanagement.com/blog/problem-statement-template/) (2026)
- **본안 적용 및 해석**: 표준 워크숍이 90~100분을 쓰는 작업을 우리는 커리큘럼상 30분 안에 얹어야 한다. 그래서 **다섯 프롬프트를 그대로 쓰지 않고, 기존 #45의 "입력·처리·출력·현실의 행동" 4칸으로 대체**한다. 이 4칸은 표준 프롬프트보다 칸이 적으면서도 (a) 데이터 가용성(입력), (b) 기술 실현성(처리), (c) 산출물 형태(출력), (d) 임팩트(현실의 행동)를 모두 강제하므로, **바이브 코딩 MVP라는 맥락에서는 오히려 더 적합하다.** 기존 슬라이드의 자산 중 가장 값진 한 장이며, 이를 중심에 놓는 것이 이번 재구성의 핵심 결정이다.

### 4-5. 동종 강의(바이브 코딩 워크숍)의 구성

- 2026년 비개발자·창업자 대상 바이브 코딩 워크숍들은 **Claude Code + GitHub + Vercel + Supabase** 스택으로 "작동하는 웹앱 배포"를 결과물로 잡고, 프롬프트 패턴·디버깅 전략 같은 **반복 가능한 툴킷**을 전달하는 구성을 공유한다. LEARN 데이와 BUILD 데이를 분리하거나, 소규모 코호트 + 라이브 코딩 형태를 쓴다.
  - [DataCamp — Summer Vibe Coding Camp](https://events.datacamp.com/summer-vibe-coding-camp)
  - [Designlab — Vibe Coding Course & Bootcamp](https://designlab.com/advanced/vibe-coding-course)
  - [Bay Area Founders Club — AI Vibe Coding Workshop: The 4-Part Masterclass](https://bayareafoundersclub.substack.com/p/ai-vibe-coding-workshop-the-4-part)
- **본안 적용**: 현재 슬라이드의 스택 선정(#30)은 업계 표준과 일치하므로 **내용은 옳고 분량만 과하다** — 4장(#31~#34)을 지우고 1장(#30)만 남긴 판단의 근거.
