## 0. 한 줄 요약

> 두 책은 같은 말을 한다. **제품이 아니라 고객의 문제에서 출발하고, 오늘의 계획은 가설로 다루며, 작게 만들어 사람에게 보여주고 배운 만큼 고쳐라.**
> 『Running Lean』은 그 **절차**(무엇을 어떤 순서로 확인할지)를, 『핑크 펭귄』은 결과를 고객에게 **전달하는 법**(핵심 가치·이름·디자인)을 준다.

## 1. 창업 초기 아이템 기획·개발에서 중요한 것 — 정의

### 1-1. 출발점

| # | 원칙 | 요지 | 출처 |
|---|---|---|---|
| 1 | 질문이 바뀌었다 | 만드는 비용이 싸질수록 "만들 수 있나"보다 "정말 만들어야 하나"가 중요해진다 | RL 서문(에릭 리스) p.12 |
| 2 | Plan A는 대부분 틀린다 | 성공한 스타트업의 약 2/3는 처음 계획과 다른 길로 갔다. 비결은 더 좋은 아이디어가 아니라 자원이 떨어지기 전에 통하는 계획을 찾은 것 | RL 소개 p.18 |
| 3 | 제품 우선 사고를 버린다 | "저는 ○○를 팝니다"로 시작하면 모두 똑같아 보인다(펭귄 프라블럼). 조금 다른 건 달라 보이지 않는다(22℃→22.5℃ 비유) | PP 1장 |
| 4 | 고객은 해결책이 아니라 자기 문제에 관심 | 린 캔버스에서 해결책 칸이 1/9뿐인 이유. 해결책은 최대한 늦게 확정한다 | RL p.30–31, p.59–60 |
| 5 | 한 고객 유형에 집중 | 모두를 노리면 흐려진다. 페이스북도 하버드 학생부터. 치과의사만 고객으로 삼은 자산관리사가 5명에서 300명 이상으로 | RL p.49, PP 2장 |
| 6 | 고객은 해결책을 설계해주지 않는다 | '더 빠른 말' 일화 — 고객은 문제와 니즈를 말할 뿐, 해결책은 창업자의 몫 | RL p.19 |

### 1-2. 문제를 정의하는 법

| 원칙 | 요지 | 출처 |
|---|---|---|
| 해결할 가치가 있는 문제의 세 조건 | 꼭 필요한가(must-have) / 돈을 낼 만한가, 아니면 누가 대신 내나(viable) / 기술적으로 풀 수 있나(feasible) | RL p.33 |
| 문제는 최대 3개, 그리고 기존 대안 | 지금은 어떻게 해결하나. 가장 큰 경쟁자는 이메일이나 '아무것도 안 함'일 수 있다 | RL p.53 |
| 고객 ≠ 사용자 | 돈을 내는 사람과 쓰는 사람을 구분한다 | RL p.49, p.53–54 |
| 얼리어답터 | 주류가 아니라 지금 가장 절실한 사람부터 | RL p.54 |
| 최상의 이득 | 2차적 이득(멋진 웹사이트)이 아니라 최상의 이득(손님이 늘어남)을 말한다 | PP 6장 |
| UVP(핵심 가치) | 기능 → 혜택 → '완성된 스토리'(이력서 예: 템플릿 → 돋보이는 이력서 → 원하던 회사 합격). 원하는 결과 + 시간 + 반박 해소. 최소한 '무엇'과 '누구' | RL p.56–57 |
| 콘셉트 토네이도 | 여러 일을 하면 설명이 안 된다 → 고객의 최상의 이득 하나로 묶어 이름을 붙인다 | PP 13장 |

### 1-3. 확인하는 법 (검증)

| 원칙 | 요지 | 출처 |
|---|---|---|
| 가장 위험한 것부터 | 리스크 = 일어날 확률 × 틀렸을 때 손실. 제품·고객·시장 리스크. 모델 우선순위: 고통 수위 > 도달 용이성 > 가격·마진 > 시장 규모 > 기술 실현성 | RL p.74–78 |
| 반증 가능한 가설 | "[구체적이고 반복 가능한 행동]을 하면 [측정 가능한 결과]가 나올 것이다". 예: 블로그 글 1편 → 가입 100명 | RL p.90–91 |
| 배우기 위한 가장 작은 일 | 드롭박스의 3분 데모 영상, 음식 트레일러, 손으로 식단표를 만들어 준 컨시어지 MVP | RL p.89–90 |
| 정성 먼저, 정량 나중 | 불확실성이 클수록 적은 데이터로 많이 배운다. 5명으로도 강한 신호가 나올 수 있다 | RL p.91–92 |
| 초기엔 설문·포커스그룹을 피한다 | 질문을 이미 안다고 가정, 보기 강요, 표정을 못 봄, 집단사고 | RL p.99–100 |
| 말이 아니라 행동 | "절실해요"보다 "지금 어떻게 해결하나". 아무것도 안 하고 잘 지낸다면 급하지 않은 문제 | RL p.102–103 |
| 학습 프레임 | 팔러 가지 말고 배우러 간다. 스크립트 사용, 인터뷰 직후 5분 기록, 2인 1조 | RL p.102–105 |
| 친구·가족의 칭찬은 데이터가 아니다 | 연습용으로만 쓴다 | RL p.109 |
| 가격 묻는 법 | "얼마면 사겠어요?"가 아니라 "X원을 생각하는데 어떠세요?". 가격도 제품의 일부 | RL p.64–65, p.132 |
| 문제 인터뷰 종료 기준 | 10명 이상 만나고, 얼리어답터 프로필·꼭 필요한 문제·현재 해결 방식을 파악했을 때 | RL p.125 |
| 공유와 피드백 | 캔버스를 적어도 한 명에게 보여준다. 갓 나온 아이디어는 인큐베이터 순서(좋은 점 → 방법 → 걸림돌)로 | RL p.73, PP 25장 |

### 1-4. 만드는 법 (MVP)

| 원칙 | 요지 | 출처 |
|---|---|---|
| MVP의 정의 | 버그 많은 시제품이 아니라, 가장 중요한 문제를 충분히 풀어 주는 최소한 | RL p.64 |
| 범위 줄이기 | 빈 슬레이트에서 시작, 문제 1번부터, 꼭 필요 / 있으면 좋음 / 불필요로 나눈다 | RL p.150–151 |
| 데모 원칙 | 실현 가능한 형태, 완성품처럼 보이게, 빠르게 반복, 진짜 같은 데이터(lorem ipsum 금지) | RL p.130 |
| 첫 화면 | 방문자는 대부분 8초 안에 떠난다. 헤드라인 = 핵심 가치, 시각 자료, 분명한 다음 행동 | RL p.154–155 |
| 핵심 행동(활성화) | 가입부터 가치를 처음 느끼는 순간까지의 흐름을 설계한다 | RL p.152–153 |
| 디자인은 신뢰 | 기능이 같으면 보기 좋은 쪽을 믿고 더 쉽게 쓴다(ATM 실험). 필요할 때마다 덧대면 파편화 | PP 15장 |
| 이름 | 무형의 아이디어는 이름이 붙어야 기억된다. 짧게, 약어 금지. 완벽한 이름에 목매지 말 것 | PP 12장 |

### 1-5. 고치고 키우는 법 (업데이트)

| 원칙 | 요지 | 출처 |
|---|---|---|
| 기능 밀어붙이기 금지 | 기능은 밀어 넣는 게 아니라 고객이 끌어당기는 것. 기능이 늘면 핵심 가치가 흐려지고 숨은 비용이 붙는다 | RL p.170–171 |
| 80 : 20 | 출시 직후엔 80%를 기존 기능 개선에, 20%만 새 기능에 | RL p.171–172 |
| 진행 중 작업 제한 | 방금 배포한 기능의 효과를 확인하기 전엔 다음 기능에 착수하지 않는다 | RL p.172–173 |
| '완료'의 정의 | 배포가 아니라 검증된 학습 | RL p.173 |
| 기능 요청 처리 | 지금 필요한가? 작은 수정인가? | RL p.175 |
| 기능 수명주기 | 문제 가치 확인 → 목업 → 데모 → 코드 → 부분 배포 → 전체 배포. 효과 없으면 폐기 | RL p.175–177 |
| 지속적 배포 | 작은 단위로 자주. 배포 안 된 코드는 재고. 원클릭 롤백. 문제가 생기면 5 Whys로 뿌리를 찾아 재발 방지 | RL p.151–152, p.202–204 |
| 허영 지표 vs 행동 지표 | 방문자 수·다운로드 수가 아니라 특정 행동과 연결된 지표. 지표 뒤에는 사람 | RL p.156–157 |
| 사람에게 보여주기 | "아무것도 누르지 말고 무슨 서비스 같은지 말해 주세요", 생각을 소리 내어 말하게 | RL p.163 |
| 배운 것 기록 | 예상한 것 / 실제로 본 것 / 다음에 할 것 | RL p.93–94 |
| 새로움 | 빅아이디어도 낡는다. 계속 새로 만든다 | PP 19·27장 |
| 올드 팩토리 / 뉴 팩토리 | 기존 일을 돌리면서 새 것을 옆에 짓는다 | PP 26장 |

## 4. 반영하지 않은 것과 이유

| 항목 | 이유 |
|---|---|
| 캔버스의 채널 · 비용 구조 · 불공정한 장점 칸 | 하루 실습 범위 밖. RL도 불공정한 장점은 PMF 근처에서 확인하라고 한다(p.97–98). 사이트에는 "오늘은 비워 둔다"고만 적음 |
| 투자 유치 시점 (PMF 이후가 적기) | 강의 범위 밖. 창업팀에게는 강사가 말로 전하길 권함 (RL p.36–37, 192–193) |
| 코호트 분석 · 전환 대시보드 · 숀 엘리스 40% 테스트 · 성장 엔진 | 사용자가 거의 없는 MVP 첫날엔 과함. 출시 뒤 참고 자료로 남김 (RL 10·14장, p.182) |
| 줄 세우기 · 희소성 연출 | 저자 스스로 '조작'이라 인정한다(PP 20장). 강의에서 권하기엔 윤리 논란이 있어 제외 |
| 세 가지 박스(가격 3단) · 구르메 옵션 · 공짜 가치 | 가격 페이지를 만들 때 쓸 전술. 오늘 MVP 범위 밖이라 제외 — 필요하면 강사 노트나 5장에서 (PP 3·21·22장) |
| 3C · 가치 피라미드 · 빅아이콘 · 테마 | 서비스업 포지셔닝 전술. 문제 정의·업데이트 단계와 직접 연결이 약함 (PP 8·9·11·16장) |

## 5. 강사 노트 — 말로 덧붙이기 좋은 한 줄

- "아이디어를 누가 훔쳐갈까 걱정하지 마세요. 대부분은 관심조차 없습니다." — 저자가 가장 먼저 깨달은 것이 '스텔스 모드는 나쁜 선택' (RL p.22)
- "아무도 원하지 않는 것을 만들기에 인생은 너무 짧다" (RL p.22)
- "고객 10명이 전부 '노'라면, 그것도 이미 의미 있는 결과다" — 에릭 리스 (RL p.108)
- "두려움이 드는 아이디어라면 좋은 신호다" (PP 25장)
- "책도 큰 소프트웨어처럼 완성되는 게 아니라 출시될 뿐이다" — 서비스도 같다 (RL p.47)

## 6. 주의

- RL 번역본은 원서 2판을 옮긴 자료다. 슬라이드나 사이트에 인용할 때는 "『Running Lean』(애쉬 마우리아)"로 표기하고, 쪽수는 이 PDF 기준이다.
- '5명으로 문제의 85% 발견'은 RL이 사용성 연구(Nielsen·Krug)를 인용한 것이지 1차 출처가 아니다 (p.92).
- '성공 스타트업의 2/3가 Plan A와 다른 길'도 RL 본문의 서술이며, 원 통계 출처는 책에 없다 (p.18). 슬라이드 핵심 수치로 쓰려면 "『Running Lean』에 따르면"으로 완충할 것.
- PP의 사례(치과의사 자산관리사, ATM 실험, 1년 동안 이름을 못 정한 사업가)는 저자의 코칭 경험담이나 2차 인용이다.
